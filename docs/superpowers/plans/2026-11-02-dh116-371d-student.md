# DH116 371D Student Implementation Plan

**Goal:** Implement the approved strict 24D/371D contract, immutable checkpoint derivation and gated native verification before any reward ablation or PPO continuation.

**Architecture:** Keep legacy 351D execution available. An opt-in completed-interval feedback observer appends 20 physical/control-readback fields. One canonical action schema and digest binds the new observation contract, checkpoint and corrective labels. No Teacher controller executes Student actions.

**Tech Stack:** Python, PyTorch, pytest, Isaac Sim, SSH, Git.

## Stage 1 — Contract and physical feedback

- [ ] Add `tabletop_surface_contract.py`: canonical JSON SHA, ordered 24D semantics and 20D feature schema; reject 26D/mismatched metadata.
- [ ] Add `tabletop_surface_feedback.py`: accumulate native substep feedback; publish completed control intervals; reset selected slots; isolate invalid rows.
- [ ] Wire explicit `--surface-feedback` through task/CLI; retain the exact 351D prefix and original reward profile.
- [ ] Add red/green tests for units, timing, invalid rows, action axes and unchanged controller limits.

## Stage 2 — Immutable checkpoint derivation

- [ ] Add `tabletop_surface_checkpoint.py` plus CLI: append zero actor/critic input columns and corresponding PPO and auxiliary Adam moments; preserve every other field and RNG.
- [ ] Save source/derived file SHA and old/new semantic contract SHA in exclusive new files.
- [ ] Test complete state retention and deterministic old-input action equivalence; reject unknown topology, stale SHA, 26D and overlapping output paths.

## Stage 3 — Native consistency gates

- [ ] Capture terminal diagnostics before automatic reset, including hold/drift/contact/support and requested versus accepted motion.
- [ ] Run Teacher replay baseline and feedback variant with unchanged 24D execution; bind provenance explicitly for legacy qualified source files.
- [ ] Run deterministic 351D/371D Student A/B from the same reset family; prove action consistency and report physical metrics without claiming performance improvement.

## Stage 4 — Corrective labels and PPO (only after Stage 3 passes)

- [ ] Record actual Student pre-failure states; produce bounded Teacher 24D labels from those states, never execute Teacher support in the Student rollout.
- [ ] Keep corrections in a distinct auxiliary pool; hash state, contract, Teacher source and safety diagnostics.
- [ ] Verify baseline-reward PPO continuation with complete state preservation and a separate output checkpoint.

## Stage 5 — Reward ablations (only after preceding gates pass)

- [ ] Isolate effective-contact height delta, hold milestones, slip, contact-break, measured support margin and action smoothness into separately selectable reward factors/scalars.
- [ ] Run exactly one changed reward factor per experiment; save native metrics, profile and complete checkpoint independently.
- [ ] Do not start long 4096-env training or claim stable Student grasp from aggregate reward or unit tests.

## Release

- [ ] Independent review; required CPU/native evidence; README and CHANGELOG with fresh commands and limits.
- [ ] Commit and push `11-2`; verify remote commit SHA. Exclude runs, checkpoints, credentials and logs.
